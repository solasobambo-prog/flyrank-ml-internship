Abstract

Which visible pages on a content site are under capturing clicks relative to how well they already rank, and which of those deserve a content editor's attention first? This project builds a tier adjusted CTR gap rule on FlyRank's anonymized search performance data, comparing each page's click through rate only to others at the same position tier, then splits flagged pages into three archetypes, a genuine CTR gap, a likely tracking anomaly, and page one content that has gone stale, each routed to a different owner. A machine learning model was also tested as an alternative to the rule and honestly failed its own validation (a negative R² under a client grouped split), confirming the simpler, transparent rule as the right choice for this data rather than a fallback. The final ranked queue flags 36.8% of visible pages across the three archetypes, with a volume dampened ranking that materially changed which pages rank highest compared to a naive volume times gap score. This is a decision support tool for content editors and SEO reviewers, not a causal claim about what drives clicks or how search ranking works.

Contents

01 Introduction

A page can rank well and still underperform. It can sit on page one of search results, earn real impressions, and still capture far fewer clicks than other pages in the same position, a signal that something about how it presents itself, its title, its description, its snippet, isn't earning the click its ranking has already won. For a content team managing hundreds or thousands of pages, the question isn't whether this happens, it's which pages it's happening to, and which of those deserve attention first.

This is a decision problem, not a curiosity. A content editor or SEO reviewer has limited hours and a long list of pages that could plausibly use a look. Reviewing a page that didn't need it wastes that time. Missing a page that did need it means a click through rate gap keeps costing traffic, unnoticed, for another review cycle. The right tool for this decision has to do three things a simple gut check can't: account for the fact that expected click through rate varies enormously by how well a page already ranks (a page on page one should expect roughly 6× the click through rate of a page buried on page three), separate a genuine content problem from a tracking or instrumentation problem that looks identical in the raw numbers, and rank the result by how much a fix is actually worth, not just by how many people saw the page.

This project builds that tool on FlyRank's anonymized search performance data: a rule that compares each page's click through rate only to its own position tier's average, splits flagged pages into three distinct categories based on likely cause, and ranks each category by a dampened estimate of opportunity rather than raw traffic size alone. A machine learning alternative was tested and honestly rejected, not because modeling failed as an idea, but because it failed its own validation on this data, a finding treated as informative rather than as a setback to hide. What follows documents the data, the method, the validation, the honest limitations, and the resulting ranked recommendations, built to be reviewed by a human, not to replace one.

02 Data

This work uses FlyRank's anonymized starter dataset, one row per content page, 30,000 rows, 44 columns, spanning 32 pseudonymized clients, with all metrics aggregated over a trailing 90 day window. No client names, domains, URLs, raw search queries, or credentials appear anywhere; content and client identifiers are pseudonymous and used only for grouping.

Pages with fewer than 500 impressions in the window were excluded from the ranked queue as too low volume to trust, though they remain visible elsewhere in the dataset. Two columns, trend_direction and trend_pct, were excluded from every stage of this project as features, since the dataset's own documentation flags them as the direct source of a label used elsewhere in the internship, using them as inputs would be circular.

A larger warehouse release (roughly 79 million daily performance rows) exists and was not required for this lane; the starter slice already provided sufficient volume for a valid, reproducible result.

This was confirmed at every stage of the project: no client name, domain, URL, or raw search query appears anywhere in this repository's work/ directory.

03 Methodology

Label

Since no outcome label exists in this data, FlyRank doesn't record "this page underperformed", a proxy was constructed: ctr_gap, a page's click-through rate minus the average CTR for pages at the same search position tier, computed only for pages with enough impressions (100+ in the trailing 90 day window) to trust the comparison.

Baseline

A transparent rule flags a page when its CTR sits below its own tier's average, weighted by traffic volume. This isn't a fallback, it's the method this project ultimately ships, chosen because it beat every model alternative tested.

Model attempt and validation design

A Random Forest and a Linear Regression were trained to predict ctr_gap from content and keyword characteristics (content type, search intent, freshness, age, search volume, competition, cost-per-click, word count), features confirmed independent of the label itself. Models were evaluated with a client-grouped split (80/20), never a random row split, since pages from the same client share editorial patterns that a random split would let a model memorize rather than generalize from.

Leakage checks

Three separate, deliberate leakage tests were run:

  1. Adding the click-through rate itself as a "feature" produced a perfect but meaningless R² of 1.000, versus an honest 0.002 without it, confirming a suspiciously good score is a warning sign, not a win.
  2. Comparing a naive random split against the honest grouped split on the same model showed the random split produced misleadingly positive results (R² of 0.04 to 0.09) purely because most clients leaked across train and test, while the honest split revealed the true, negative result.
  3. Deliberately reintroducing a known leaky feature into the otherwise honest pipeline pushed R² from −1.57 up to 0.92, confirming the evaluation method correctly detects a real leak when one exists, so the negative results elsewhere reflect a real finding, not a broken test.

Result and root cause

Neither model beat the baseline rule, and both scored worse than simply predicting the training average. Root-cause analysis traced most of the Random Forest's error to a single outlier client whose behavior didn't resemble any other client in the dataset; removing that one client from training brought the score close to the trivial baseline, confirming the model had memorized one client's noise rather than learned a generalizable pattern.

Conclusion. Content and keyword metadata do not meaningfully explain this CTR gap in this dataset. The rule-based baseline was kept and refined into three distinct categories of flagged pages, a genuine CTR gap, a likely tracking issue, and stale page-one content, each validated independently before being combined into the final ranked recommendation queue.

05 Limitations & honest framing

This work is decision support for content editors, SEO reviewers, and, where a tracking anomaly is flagged, engineering, not a tool for automated publishing, grading contributors, or promising a client a specific recovery.

The findings come from a 30,000 row anonymized sample across 32 clients, a trailing 90-day snapshot, not FlyRank's full inventory. The core metric, a page's CTR gap against its position tier's average, is a constructed proxy rather than an outcome FlyRank measures directly, and that average is a snapshot of this sample, not a fixed constant. Several model features had meaningful missing data (up to 26% for word count), imputed rather than discarded, a real source of noise layered on top of an already negative modeling result.

Two of the three page archetypes carry known, disclosed weaknesses: the CTR-gap category structurally under-covers pages already ranking in the very top positions, and the stale-content category, after requiring genuine staleness on two separate measures, has only 15 qualifying pages, all sharing the same content type and position tier, too small and too confounded to treat as a stable pattern rather than a starting point for a closer look.

No causal claim, and no claim about Google's ranking algorithm. Every recommendation in this queue points at a page worth reviewing, not a diagnosis, a guaranteed fix, or a claim about why a page ranks where it does. This project makes no attempt to model or explain Google's ranking algorithm, and no result here should be read as evidence that any specific action will cause a measurable change in performance.

06 Ranked recommendations

The output is a ranked queue of pages worth a human look, split into three categories, each with a different owner.

What should never be automated

  • Auto-editing or auto-publishing titles, meta descriptions, snippets, or content.
  • Treating a flag as a performance review of a writer or editor.
  • A client-facing promise built on the estimated impact figure, a sizing estimate, not a tested recovery number.
  • Reintroducing the failed model as a confidence weight on top of the rule.
  • Routing tracking-gap rows to content editors by default; they belong with engineering first.
  • Collapsing the three reason codes into one blended score, the split exists because each implies a different owner and a different check.

Human review before acting

  • Confirm impressions still clear the archetype's floor against current data, not the snapshot this queue was built from.
  • Confirm a zero-CTR flag in the actual analytics account before looping in content.
  • Check days since last update before queuing a refresh a page may have already received.
  • Review the 15 decay-risk rows individually, given the small sample, rather than trusting the count as a pattern.

Monitoring / retrain triggers

  • A shift in the reason-code mix, especially a rising tracking-gap share.
  • Tier-average CTR drift as search behavior changes over time.
  • A content-type mix shift, given how concentrated one content type already is in this dataset.
  • A materially larger, more diverse dataset, the only condition worth revisiting the abandoned model approach.

To rerun: clone the repository, open any notebook in Google Colab (each has an "Open in Colab" badge), and run all cells top to bottom. Every notebook re-clones the repository if needed and reads directly from data/raw/content_refresh_anonymized.csv, no manual setup beyond that.

All model training and splitting uses random_state=42, so results are exact and reproducible on a fresh run, not just directionally similar. The ranked queue CSV is excluded from the repository by design (a CI leak guard) and regenerates automatically from w07_action_playbook.ipynb; a committed monitoring baseline JSON serves as the metrics receipt a future run can check its own numbers against.

This project runs on Google Colab's standard Python environment, no custom package installs beyond what Colab provides by default. Model results use scikit-learn's default GroupShuffleSplit, RandomForestRegressor, and LinearRegression implementations; exact library versions were not pinned, a limitation worth noting for strict reproducibility.
